# pq-accounts

Deployable Starknet account contracts backed by the verifiers in this repository.

`contracts/src/accounts/` holds one account per verifier scheme: `EcdsaStarkAccount`
(classical control), `Falcon512ShakeAccount` (60-felt hint signature), and
`Falcon512ShakeDirectAccount` (31-felt direct signature). The two Falcon accounts embed
the verifier-generic account component (`contracts/src/utils/account.cairo`) with their
verifier; the shared interfaces, execution checks, and key storage live beside it in
`contracts/src/utils/`.

## What a Falcon account does

- **SNIP-6 entrypoints:** `__execute__`, `__validate__`, `__validate_declare__`,
  `__validate_deploy__`, `is_valid_signature`, and `supports_interface` (SRC5 and SRC6).
  `__execute__` accepts only the protocol as caller and transaction version 1 or later.
- **Key validation:** the constructor and key rotation store a key only if the verifier's
  `is_valid_public_key` accepts it: exactly 29 felts, each a canonical base-Q packing of
  NTT-domain coefficients in `[0, q)`. A malformed key can never be installed.
- **Key storage:** the key sits in consecutive storage slots from one fixed base (length
  first, then the felts), so validation reads it with one storage read per felt and no
  address hashing.
- **Key rotation:** `set_public_key(new_public_key, signature)` runs only as a self-call,
  so the current key authorizes it through `__execute__`. `signature` must be a valid
  signature by the new key of `get_public_key_rotation_hash(new_public_key)`:

  ```text
  poseidon_hash_span([
      'PQ_ACCOUNT_SET_PUBLIC_KEY', chain_id, account_address,
      poseidon_hash_span(current_key), poseidon_hash_span(new_key),
  ])
  ```

  This proves the new key is held and binds the proof to one chain, one account, and one
  transition. It emits `PublicKeyRemoved` and `PublicKeyAdded` with the keys' Poseidon
  hashes.
- **Upgrades:** `upgrade(new_class_hash)` runs only as a self-call, rejects the zero class
  hash, replaces the class, and emits `Upgraded`. The key survives the class change.

Signatures use the SHAKE-256 hash-to-point of the Falcon round-3 specification over the
transaction hash, so round-3 Falcon-512 signers (falcon.py, PQClean, liboqs) can produce
them, and FN-DSA signers cannot, because FIPS 206 frames the message differently; the hint
account additionally needs `s1 * h`, which anyone can compute from the public signature
and key. Signing is off-chain; this repository ships no key material.

The contracts compile against Starknet's audited libfunc list, the list a network
enforces when a class is declared, and the build fails on any libfunc outside it.

## Tests

`contracts/tests/accounts.cairo` runs every scenario against both Falcon accounts with
genuine falcon.py signatures: key validation at deployment, transaction, declare, and
deploy validation, `is_valid_signature`, the `__execute__` guards, rotation (including its
chain-id binding and a cross-check of the off-chain rotation hash), and upgrades. The
second keypair and its signatures in `contracts/tests/fixtures.cairo` are generated by
`scripts/gen_account_fixture.py`.

The benchmark accounts under `crates/bench_targets` embed the same component and remain
measurement harnesses. The contracts here are the accounts intended for on-chain
interaction.
